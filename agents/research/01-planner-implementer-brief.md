# Planner & Implementer Agent Design Brief — Sweep 1

Synthesized from five parallel research sweeps (official Anthropic guidance, framework plan-and-execute patterns, the multi-agent failure literature, spec-driven development, and real prompt artifacts) plus three targeted gap-fills. Run: `wf_aed4f28a-204`, 10 agents, ~1.31M tokens, 393 tool calls.

## Principles

- **The plan is the only channel. Everything the implementer needs must be IN the plan text — exact repo-relative file paths, symbol names, the literal build/test commands — because the implementer's context starts cold and receives nothing else.**
  - *Applies to:* both
  - *Why:* Five independent sweeps converge on this as mechanism, not style. Anthropic states it flatly: 'The only content you pass from parent to subagent is the Agent tool's prompt string.' CrewAI's delegate_work tool description: 'they know nothing about the task, so share absolutely everything you know, don't reference things but instead explain them.' deepagents: 'Each invocation is stateless.' The HKUST Planner-Coder Gap study names 'context fragmentation, where the coder loses access to crucial constraints... implicit in the original requirements but not explicitly preserved in the plan' as one of two root mechanisms behind 700+ hand-root-caused failures. Referential delegation ('fix the bug we found', 'apply the same pattern', 'based on your findings') is unresolvable from a cold context and the implementer either guesses a file or burns its budget re-exploring.
  - *Confidence:* well-established
  - *Concrete implication:* Planner agent.md gets a hard rule: 'Every task must be executable by someone who has never seen this conversation. Before emitting the plan, reread each task and delete any reference that cannot be resolved from the plan text alone.' Implementer agent.md gets the matching rule: 'If a task references something you cannot resolve from the plan text, return OUTCOME: bad-dispatch and name the unresolvable reference — do not guess.' Ban the literal phrasings in the planner file: 'never write "based on your findings", "the file from step 2", "the same pattern", or "the bug we discussed".'
- **Enforce the planner's write scope at the tool layer with ONE writable path — the plan artifact — not with a prose prohibition and not with a blanket no-write rule.**
  - *Applies to:* planner
  - *Why:* Prose prohibitions leak under pressure (MAST FM-1.2 Disobey Role Specification). CrewAI treats a manager with tools as unrecoverable and `raise Exception("Manager agent should not have tools")`. Roo's architect ships `groups: ["read", ["edit", {fileRegex: "\\.md$"}], "mcp"]` — writing a .ts file is mechanically impossible, so the body never has to say 'do not write code.' But a blanket no-write rule is the wrong correction: somebody has to author the plan file, and Claude Code's own plan mode says 'Write your final plan to the plan file (the only file you can edit).' Codex draws the boundary at repo-tracked mutation rather than at command execution, explicitly permitting test/build runs that write to `target/` or `.cache/` — a planner that cannot run the test suite cannot validate feasibility, which is the highest-value thing a planner does.
  - *Confidence:* well-established
  - *Concrete implication:* Planner frontmatter: `tools: Read, Grep, Glob, Bash, Write` with the body stating 'The ONLY file you may create or edit is the plan artifact at <PLAN_PATH>. Every other path is read-only.' Where the harness supports path scoping (Roo fileRegex, permission rules), scope Write to the plan path/extension. Do NOT rely on `permissionMode: plan` in Claude Code — the docs state a parent running bypassPermissions/acceptEdits/auto overrides it silently. Add the Codex boundary verbatim: 'You may run tests, builds, linters, and read-only git commands. You may not create, edit, delete, move, or copy any repo-tracked file other than the plan.'
- **Pick ONE handoff channel and name it identically in both agent files. The default should be hybrid: the invocation prompt carries a POINTER to the plan file plus a task-scoped PROJECTION of it; the file remains the durable store.**
  - *Applies to:* both
  - *Why:* Three topologies ship in production (return-text, file-on-disk, inlined-content) and each makes ~15 other lines in both prompts wrong if mismatched. A planner written for one and an implementer written for another produces an implementer that either re-plans from scratch or waits for a file nobody wrote. Inlining the whole plan re-pays full token cost per spawn and drowns a single-task implementer in irrelevant phases; passing a bare path makes it re-read and re-interpret the whole document, which is where scope creep enters. rails_ai_agents composes seven named slices ('Extract only the Technical Context, Project Structure... not the full plan'). handoff-kit passes only a slug. Post-compaction the file wins mechanically: conversation content is summarized away and does not come back, files are re-read from disk (measured: 0/10 synthetic facts survived in 106/108 compactions with no file backing).
  - *Confidence:* reasonable-consensus
  - *Concrete implication:* Both files open with the same sentence naming the channel, e.g. 'The plan lives at <PLAN_PATH>. The dispatch prompt carries that path plus only the sections relevant to this task.' Planner file: 'Write the full plan to <PLAN_PATH> BEFORE spawning anything, and re-read it rather than relying on conversation history.' Orchestrator section: 'Each dispatch includes (a) the plan path, (b) only the task's own section plus shared context, (c) a list of files prior tasks already created.' Implementer file: 'Re-read the plan artifact at the start of every work unit; do not rely on what you were told at spawn.' Never use Claude Code's native `~/.claude/plans/<random-slug>.md` as the handoff store — it is outside the repo, randomly named, and reset by /clear.
- **Every task carries a machine-checkable DONE criterion — a literal command and its expected result — and the plan ends with one end-to-end verification step.**
  - *Applies to:* both
  - *Why:* Anthropic's whole agent-loop framing is gather→act→verify, and their best-practices lead is 'Claude stops when the work looks done. Without a check it can run, "looks done" is the only signal available.' CrewAI: 'Each step must have a clear DONE criterion.' Anthropic's spec bar: specs 'end with an end-to-end verification step that proves the feature works.' Kiro converts EARS acceptance criteria into property-based tests mechanically. MAST measured the effect: adding a high-level task-objective verification step was worth +15.6% on ChatDev/ProgramDev — more than double the +9.4% from improving role specifications. And it fails in both directions without it: FM-1.5 Unaware of Termination Conditions (9.8–12.4%) makes agents loop; FM-3.1 Premature Termination (6.2–7.8%) makes them hand back half-work as complete.
  - *Confidence:* well-established
  - *Concrete implication:* Plan template requires per task: `DONE: <exact command>` + `EXPECT: <exit 0 / named assertion>`. Planner rule: 'If you cannot state a runnable check for a step, the step is not ready to hand off — split it or make its artifact concrete.' Plan must end with a `## Verification Plan` split into `### Automated` (exact commands, exit-0 expectations) and `### Manual`, plus one end-to-end check proving the feature works. Implementer rule: 'Only report a task done after running its DONE command and observing EXPECT. Paste the command and the last 20 lines of output into your report.'
- **Judge step completion on artifacts and exit codes, never on the implementer's narration. Enumerate the disqualifying patterns rather than saying 'verify the work'.**
  - *Applies to:* planner
  - *Why:* MAST's Reasoning-Action Mismatch (13.98%) plus No/Incomplete Verification (6.82%) is ~21% of all observed multi-agent failures — the orchestrator believing a claim the artifacts contradict. Claude Code's shipped coordinator prompt states the epistemic gap precisely: 'a worker's summary describes what it intended to do, not necessarily what it did. When a worker reports code changes as done, check the actual diff before relaying success.' CrewAI enumerates the disqualifiers concretely: exploratory-only output (ls/pwd/cat) with no artifact, non-zero exit not recovered, a create/build/start step whose result shows it was not done, ran out of attempts. An outcome-verifying orchestrator implements the same idea as git_diff against a recorded base SHA, with the transcript demoted to `required: false`.
  - *Confidence:* well-established
  - *Concrete implication:* Planner file gets a literal acceptance checklist: 'Mark a task complete ONLY if: (1) `git diff <base_sha>..` shows changes in the files the task owns, (2) the task's DONE command exited 0 with output pasted in the report, (3) every file the task said it would create exists. Reject and re-dispatch if: the report is exploratory only, an exit code was non-zero and unexplained, or a create/build/start task shows no matching artifact. The implementer's own claim of success is the weakest evidence and never sufficient on its own.' Planner records the base SHA before dispatch and passes it in.
- **Decompose by file/module ownership, never by lifecycle phase of one unit of work. Single writer per file; fan out read-only investigation freely, serialize writes.**
  - *Applies to:* planner
  - *Why:* This is the sharpest counterintuitive finding and it is stated by both camps. Anthropic labels role-splitting one feature 'problem-centric decomposition (often counterproductive)' and reports those setups 'spent more tokens on coordination than on actual work' — 'Planning, implementation, and testing of the same feature share too much context', producing 'a telephone game where context degrades at each handoff.' Cognition's Principle 2: 'Actions carry implicit decisions, and conflicting decisions carry bad results' — the Flappy Bird case where two subagents produce individually plausible, jointly useless output. LangChain: 'read actions are inherently more parallelizable than write actions... conflicting write actions typically produce far worse outcomes.' Claude Code agent teams: 'Two teammates editing the same file leads to overwrites.' Kiro computes it mechanically: 'Tasks that touch the same files are never run in parallel.' Four independent camps agree — this is the most robust finding in the whole corpus.
  - *Confidence:* well-established
  - *Concrete implication:* Planner file: 'Each task names the files it OWNS and may not touch any file owned by another task. Two tasks marked [P] must have disjoint owned-file sets — verify this mechanically before emitting the plan. If two pieces of work must touch the same file, they are ONE task, not two.' Add the negative rule: 'Never create separate tasks for planning, implementing, testing, and reviewing the same change — those are stages of one task with written artifacts, not separate agents.' Where the harness supports it, set `isolation: worktree` on implementers so a partial failure leaves an inspectable tree rather than a mutated main checkout.
- **The orchestrator's context holds structured summaries only, never raw transcripts or tool output — and the implementer must be TOLD its final message is all the parent will see.**
  - *Applies to:* both
  - *Why:* Two halves of one mechanism, and both are needed. Four frameworks default to last-message-only: langgraph-supervisor `output_mode="last_message"`, deepagents excludes `{messages, todos, structured_response}`, Cline's `summarizeRun()` hands the lead `truncateText(result.text, TEAM_RUN_TEXT_PREVIEW_LIMIT)`, OpenAI's flagship example ships a `custom_output_extractor` that strips sub-agent output to one summary field. Anthropic quantifies it: subagents 'might explore extensively, using tens of thousands of tokens... but returns only a condensed, distilled summary (often 1,000-2,000 tokens).' But truncation is only safe if the last message is self-sufficient — deepagents' DEFAULT_SUBAGENT_PROMPT exists as one sentence solely for this: 'The calling agent only sees your final assistant message, not your intermediate work, tool results, or status tracking. Ensure your final response contains the complete answer.' Without it, implementers write 'Done, see above' and 'above' is exactly what got dropped (MAST FM-2.4 Information Withholding).
  - *Confidence:* well-established
  - *Concrete implication:* Implementer file, near the top, verbatim-adapted: 'The planner sees ONLY your final message — not your tool calls, file reads, or intermediate reasoning. Your final message must be complete on its own. Target 300–800 words. Never write "see above" or reference anything outside your final message.' Planner file: 'Never paste raw subagent output into a follow-up dispatch. Read the report, form your own understanding, and write a synthesized spec.' Add Anthropic's one-liner: 'Leave any extensive tool calls to the workers; keep your own context for the plan and the summaries.'
- **Define every domain term operationally, and give every named edge case and conditional its expected behavior — not just its existence.**
  - *Applies to:* planner
  - *Why:* This is the single highest-measured-leverage plan-quality intervention in the literature and it targets 74% of planner-coder failures. HKUST's hand-root-caused distribution: EP-1 Gap in Core Concepts 32.7% (the plan says 'remove all duplicates' and the coder implements keep-one-of-each instead of delete-every-repeated-element), EP-5 Gap in Condition Judgments 22.1%, EP-2 Gap in Edge Cases 19.5% (the plan says 'calculate the product of signs and sum of all numbers' and the coder omits the number==0 branch because the plan never spelled it out), EP-4 Gap in Relational Phrases 9.7%. Their monitor-agent intervention, which forces exactly these to be restated at the boundary, repaired 40.0–88.9% of previously-failing cases and cut re-fuzzed failures by up to 85.7%. Critically, 75.3% of failures were plan-logically-correct-but-mis-implemented, so this is a handoff-precision problem, not a planning-quality problem.
  - *Confidence:* well-established
  - *Concrete implication:* Plan template gets a required `## Operational Definitions` section: 'For each domain term the plan uses, state exactly what it means in code terms before using it in a step.' Every task's edge-case list must be `<condition> → <expected behavior>`; the planner file bans the bare form: 'Never write "handle the edge cases" or "be careful with boundary conditions" — state the correct behavior for each.' Add the rewrite rule: 'Convert relational language to predicates: "at least as much as" → ">= (inclusive)"; "repeated twice" → "appears exactly 2 times".' Implementer file gets the echo: 'Before writing code, restate in your own words: (a) the core concepts, (b) the quantitative/relational semantics, (c) the conditional logic flow, (d) three concrete edge cases and their handling. Then implement. Then check your code against that restatement.'
- **Put a numeric effort ladder and an explicit don't-orchestrate branch in the planner, keyed to task size — do not leave fan-out to model judgment.**
  - *Applies to:* planner
  - *Why:* Unconstrained, Anthropic's own orchestrator was 'spawning 50 subagents for simple queries.' Their fix was literal numbers plus a tie-breaker: 'Prefer fewer, more capable subagents over many overly narrow ones. More subagents = more overhead.' Concrete ladders across sources: Anthropic 1 / 2-3 / 3-5 / 5-10, hard max 20; agent teams 'Start with 3-5 teammates', '5-6 tasks per teammate', '15 independent tasks → 3 teammates'; deepagents coding skill '3-10 concrete steps'; CrewAI templates 'Hard limit: {max_steps} steps'; LangChain todo middleware sets a floor 'If the user's request is trivial and takes less than 3 steps, it is better to NOT use this tool.' The negative branch is stated by three vendors: Anthropic best practices 'If you could describe the diff in one sentence, skip the plan'; the subagents doc's use-the-main-conversation list; Antigravity 'DO NOT USE THIS TOOL UNLESS THERE IS SUFFICIENT COMPLEXITY.' The cost is real: 3–10x tokens vs single-agent, ~15x vs chat, and a measured 4.2–5.9x input-token multiplier with NO latency win on non-parallel work.
  - *Confidence:* well-established
  - *Concrete implication:* Planner file gets a literal ladder: 'Single-file change or anything describable in one sentence → do it yourself, emit no plan. 2–4 independent components → 2–4 tasks. Cross-cutting change → up to 8 tasks. Never exceed 10 tasks; if a change seems to need more, consolidate.' Plus the floor: 'If the whole change fits in under 3 steps, say so and hand it back to the main session rather than planning it.' Plus the budget: 'Assume this pair costs 4–6x the tokens of doing it in one thread. State in the plan why the split is worth it.'
- **The planner writes the synthesis itself and never delegates comprehension. It must read every report and form its own understanding before dispatching follow-up work.**
  - *Applies to:* planner
  - *Why:* Anthropic prohibits it outright in their shipped lead prompt: 'NEVER create a subagent to generate the final report — YOU write and craft this final research report yourself... you are never allowed to use subagents to create the report.' Claude Code's shipped coordinator prompt bans the specific phrasings rather than the general behavior, which is what makes it enforceable: 'never write "based on your findings" or "based on the research" — those phrases hand off understanding to the worker instead of doing it yourself.' The orchestrator is the only agent that has seen all the summaries; delegating synthesis loses that. The mirror failure is naming the escape hatch: Anthropic's role statement also says 'You only conduct direct research if a critical question remains unaddressed', which prevents the orchestrator degenerating into a pure relay.
  - *Confidence:* well-established
  - *Concrete implication:* Planner file, verbatim-adapted: 'When a worker reports back, you must understand the report before directing follow-up work. Read it. Identify the approach. Never write "based on your findings" or "the worker found an issue, please fix it" — write the fix spec yourself, naming the file, the line, the cause, and the required behavior.' Add the escape hatch so it does not become a pure relay: 'Do the investigation yourself when it is faster than a spawn — a single grep, a file read, a one-line calculation. For a two-file change, investigate one file yourself rather than spawning and waiting.'
- **Give the implementer numeric HALT conditions AND an explicit anti-premature-stop rule. Both boundaries, or you get the other failure.**
  - *Applies to:* implementer
  - *Why:* Without HALT conditions an implementer grinds indefinitely on a broken approach; without an anti-stop rule it declares partial victory at an arbitrary narrative boundary. BMAD ships both in one prompt: 'HALT if new dependencies are required beyond story specifications', 'HALT after 3 consecutive implementation failures', and 'Absolutely DO NOT stop because of "milestones", "significant progress", or "session boundaries".' Osmani gives the orchestrator-side version: 'a hard MAX_ITERATIONS=8' and 'if stuck 3+ iterations on the same error, kill and reassign', plus a pre-retry reflection ('Am I repeating the same approach?'). Claude Code documents the failure this prevents at both ends: 'The lead may decide the team is finished before all tasks are actually complete' and unbounded retry loops that burn the orchestrator's context on repeated failure traces. Only BMAD ships a numeric retry budget — it is the rarest and most useful line in the corpus.
  - *Confidence:* reasonable-consensus
  - *Concrete implication:* Implementer file gets a literal HALT list: 'HALT and return immediately if — (a) the task requires a dependency not named in the plan, (b) three consecutive attempts at the same step fail, (c) required configuration or a named file is missing, (d) the task's requirements are ambiguous after re-reading the plan, (e) you would need to edit a file another task owns.' Paired with: 'Do NOT stop for milestones, significant progress, or session boundaries. Only the HALT conditions and a completed DONE criterion end your work.' Plus the anti-derailment pair from Claude Code's worker prompt: 'Do not fix unrelated issues you discover — record them as follow-ups. Do not use `git add .` or blanket staging.'
- **The plan is the contract and it wins. When the plan and observed reality disagree, the derived thing is regenerated and the divergence is recorded — the implementer never edits the plan to match what it did.**
  - *Applies to:* both
  - *Why:* Without this sentence, an implementer that hits reality diverging from the plan 'helpfully' edits the plan to match, destroying the review artifact and any chance of detecting the plan was wrong. HN practitioners report LLMs 'removing tests, or modifying acceptance criteria to make implementations pass artificially.' handoff-kit states the direction of repair explicitly: 'PLAN is the source of truth; never edit PLAN to match `.verify`' and 'The plan is the contract. If a step is wrong, ambiguous, or impossible, stop and record it in DECISIONS.md rather than improvising a different design.' spec-spine has the structurally identical rule: 'DO NOT amend an owning spec purely to make the coupling gate pass; surface the conflict instead.' BMAD makes it mechanically enforceable by scoping implementer writes: 'Only modify the story file in these areas: Tasks/Subtasks checkboxes, Dev Agent Record, File List, Change Log, and Status.'
  - *Confidence:* reasonable-consensus
  - *Concrete implication:* Split the artifact by WRITER and state ownership on each: PLAN.md (planner writes; implementer reads only), PROGRESS.md (implementer writes checkboxes + work log), DECISIONS.md (implementer appends deviations and questions). Implementer file: 'You may never edit PLAN.md. If a step is wrong, impossible, or ambiguous, append the conflict to DECISIONS.md and return OUTCOME: plan-is-wrong. Do not improvise a different design.' Planner file: 'On revision, overwrite the SAME plan path — never emit plan-v2.md. Append new remediation tasks with fresh IDs; never rewrite, renumber, reorder, or delete an existing task.'
- **Make the implementer's FIRST action a reconciliation of the plan against the working tree, before any edit.**
  - *Applies to:* implementer
  - *Why:* This is what makes a file-based handoff survive being picked up hours later, after a partial run, or by a different agent — the case the whole topology exists for. handoff-kit mandates it: 'Run `git status`, `git log --oneline -10`, and `git diff --stat` to find work done since PROGRESS.md was last updated and any spec-vs-tree drift. Then run the tiny cross-artifact consistency check: flag PROGRESS checkboxes that don't match PLAN steps, DECISIONS that contradict PLAN, and a provenance SHA far behind HEAD... if the package is internally inconsistent, surface it before implementing on a bad map.' Without it, the implementer builds on a stale map and the divergence is only found at review. This is also the only defense against the partially-applied case, since Claude Code checkpoints do not cover subagent edits or any Bash-driven mutation.
  - *Confidence:* single-source
  - *Concrete implication:* Implementer file step 1, before any edit: 'Read PLAN.md, PROGRESS.md, DECISIONS.md. Run `git status --porcelain`, `git log --oneline -10`, `git diff --stat`. Compare the plan's recorded base SHA against HEAD. If PROGRESS checkboxes disagree with the tree, if DECISIONS contradicts PLAN, or if HEAD is far past the recorded base SHA, STOP and return OUTCOME: stale-plan with the specific inconsistency. Do not implement on a bad map.' Planner file: 'Record `base_sha: <sha>` in the plan header before dispatch.'
- **Fix a small closed set of return outcomes, require each to carry artifact-level evidence, and give the planner a dispatch table mapping each outcome to a different action.**
  - *Applies to:* both
  - *Why:* The channel is an unstructured string, so the taxonomy is only real if it is explicit on both sides. SIRHAMY ships the minimal version: 'STATUS: completed | partial | failed / TASKS_DONE: X/Y / ERRORS: [...] / NOTES: [...]' and the orchestration loop branches on it. Cline's runtime version requires a completion `summary`, a blocking `reason`, `evidence[]`, and a `nextAction`. Magentic-One's progress ledger forces three INDEPENDENT booleans with `reason` before `answer` — 'not done' and 'stuck' are different states requiring opposite responses. Each outcome must map to a DIFFERENT planner action or it should be merged. Encoding constraint: do NOT use angle-bracket pseudo-XML delimiters — Claude Code scans subagent output and backslashes harness-shaped tags and turn markers, and may prepend a `[harness: ...]` line, so a strict XML parser fails exactly on reports containing quoted logs or code.
  - *Confidence:* contested
  - *Concrete implication:* Both files carry the same enum and the same encoding. Implementer file: 'End your reply with a fenced ```handoff block whose first line is `OUTCOME: <token>`, token ∈ {done, done-with-deviations, blocked-on-decision, plan-is-wrong, partially-applied, bad-dispatch}. Never use angle-bracket tags as delimiters.' Planner file gets the dispatch table: done → verify by artifact then advance; done-with-deviations → read DECISIONS, decide accept-or-revert, then advance; blocked-on-decision → answer and RESUME the same worker (never re-dispatch cold, it will double-apply non-idempotent edits); plan-is-wrong → replan that task only, append remediation tasks; partially-applied → run `git diff <base_sha>..`, decide revert-or-continue, then re-dispatch with an explicit 'what already exists' list; bad-dispatch → rewrite the dispatch, no repo state to reconcile. Plus: 'Absence of a parseable OUTCOME means UNKNOWN — route UNKNOWN to the same verification path as partially-applied, never to accept.'
- **Split unknowns into discoverable facts and preference tradeoffs, and handle them differently: explore for facts, ask for preferences with 2–4 mutually exclusive options plus a recommended default.**
  - *Applies to:* planner
  - *Why:* Planners waste user turns asking what the codebase answers ('where is this struct?', 'which UI component?') while silently guessing on genuine product tradeoffs. Codex names the two classes and gives each a rule, requiring 'at least one targeted non-mutating exploration pass' before any question, and requiring unanswered preference questions to 'proceed with the default and record it as an assumption.' MAST measures the cost of not asking: FM-2.2 Fail to Ask for Clarification = 6.8%, the second-largest inter-agent misalignment mode; HKUST separately found 9.3% of failures were irreducible ambiguity nobody surfaced. Devin's 'Don't be shy' is the counterweight to models that guess rather than ask. Spec Kit makes it grep-able with `[NEEDS CLARIFICATION: auth method not specified - email/password, SSO, OAuth?]` and errors on unresolved markers.
  - *Confidence:* reasonable-consensus
  - *Concrete implication:* Planner file: 'Two kinds of unknowns. DISCOVERABLE (anything the repo can answer: file locations, existing helpers, the actual test command) — explore first, never ask. PREFERENCE (product tradeoffs, breaking-change tolerance, scope) — ask, presenting 2–4 mutually exclusive options plus your recommendation; batch all independent questions into one turn. If unanswered, proceed with your recommendation and record it under `## Assumptions`.' Plus the gate: 'Mark any unresolved decision inline as `[NEEDS CLARIFICATION: <question>]`. A plan containing that marker is not ready to hand off.'
- **The planner's stopping rule is decision-completeness, not length or detail. Cap verbosity explicitly.**
  - *Applies to:* planner
  - *Why:* Codex ships the cleanest formulation: a great plan 'must be decision complete, where the implementer does not need to make any decisions.' This is checkable; 'be detailed' is not, and 'be detailed' has no terminating condition so planners pad. A plan can be 300 lines and still leave the implementer guessing which library to use; a 30-line plan that closes every open decision is a better handoff. Codex pairs it with anti-verbosity: prefer grouped bullets by subsystem over file-by-file inventories, 'avoid naming more than 3 paths unless extra specificity is necessary to prevent mistakes', 'do not invent detailed schema, validation, precedence, fallback, or wire-shape policy unless the request establishes it.' Claude Code's compromise for repeated changes: 'describe the pattern once and list a few representative paths — do not enumerate every file or line number.'
  - *Confidence:* reasonable-consensus
  - *Concrete implication:* Planner file: 'A plan is done when the implementer needs to make no decisions — not when it is long. Before emitting, ask: is there any choice left that I have not made? Then cut everything that is not a decision, a location, or a check.' Plus: 'For changes that repeat a pattern across many files, describe the pattern once and list 3–5 representative paths. Do not enumerate every file or line number — line numbers shift and the plan is wrong on contact.' Plus Roo's rule verbatim: 'Never provide level-of-effort time estimates (hours, days, weeks).'
- **The plan is prescriptive about WHAT and WHERE — files, interfaces, contracts, acceptance checks — and permissive about HOW the internals are written.**
  - *Applies to:* planner
  - *Why:* This resolves the real tension between 'name exact paths and symbols' and Cognition's production finding that managers become 'overly prescriptive, which backfires when the manager lacks deep codebase context' — the implementer, which does have the files open, follows the wrong instruction anyway because the plan was approved. Traycer's formulation is the clean two-sided version: 'You DO NOT write code, but you may mention symbols, classes, and functions relevant to the task.' A one-sided 'don't write code' rule produces vague architectural prose; the two-sided rule produces a plan that is precise without being a diff. Note Traycer escalates 'may' to 'should' in its deeper planning mode — specificity is the default, not an option.
  - *Confidence:* reasonable-consensus
  - *Concrete implication:* Planner file: 'You do not write implementation code. You DO name exact repo-relative paths, symbols, function and type names, and the interfaces between them. Be prescriptive about file boundaries, public interfaces, data contracts, and acceptance checks. Leave internal implementation to the implementer — if you find yourself writing the body of a function, stop and state its signature and contract instead.' Add the reuse rule from Claude Code phase 1: 'Actively search for existing functions, utilities, and patterns that can be reused; reference them with their file paths. Avoid proposing new code when a suitable implementation already exists.'
- **Read the files that will be MODIFIED (not just created) and record, per file: current state, what this change modifies, what must be preserved.**
  - *Applies to:* planner
  - *Why:* BMAD flags this <critical> and names it directly: 'READ FILES BEING MODIFIED — skipping this is the primary cause of implementation failures and review cycles.' Plans that only describe new files are the ones that break existing behavior, because the regression risk is never written down as a constraint anyone can check. BMAD's closing rule closes the loophole from the other side: 'A story implementation must leave the system working end-to-end — not just satisfy its stated ACs. If a behavior is required for the feature to work correctly in the existing system, it is a requirement whether or not it is explicitly written in the story.'
  - *Confidence:* single-source
  - *Concrete implication:* Plan template gets a required `## Files Being Modified` section, one entry per [MODIFY] file with three fields: `Current state:` (what it does today), `This change:` (what is modified), `Must preserve:` (existing interactions and behaviors this change must not break). Planner file: 'Open every file you mark [MODIFY] before writing the plan. A plan that names a file it has not read is a guess.' Implementer file: 'Your change must leave the system working end-to-end, not merely satisfy the listed criteria.'
- **Every task line is machine-parseable: checkbox, stable ID, parallel marker defined as file-disjointness, a back-reference to what it satisfies, and the file path.**
  - *Applies to:* planner
  - *Why:* Structured task lines are what make coverage analysis, dependency scheduling, and append-only revision possible at all; prose task lists cannot be audited. Spec Kit's format is `- [ ] T012 [P] [US1] Create User model in src/models/user.py` with four explicit WRONG examples each missing exactly one component — far more effective than a prose description of the format. `[P]` is defined mechanically as 'different files, no dependencies', not as a judgment. Kiro requires granular requirement back-references (`_Requirements: 2.1, 2.2`); BMAD uses `(AC: #)`. Cursor pins granularity numerically: '≤14 words, verb-led', 'at least 5 minutes of user work', 'Prefer fewer, larger todo items.'
  - *Confidence:* well-established
  - *Concrete implication:* Plan template mandates the line format with ✅/❌ examples in the planner file itself: '`- [ ] T012 [P] [REQ-3] Add LRUCache interface to src/types.ts` — ❌ missing ID, ❌ missing checkbox, ❌ missing path, ❌ missing requirement ref.' Define the marker: '`[P]` means this task shares no owned file with any other [P] task in the same phase. Verify by intersecting owned-file sets; if they intersect, drop the marker.' Cap granularity: 'Each task is verb-led, ≤14 words in its description, and represents work a human would take at least 5 minutes to do. Prefer fewer, larger tasks.'
- **The reviewer runs on clean context, sees only the diff and the plan, and is scoped to report gaps that affect correctness or stated requirements — not style.**
  - *Applies to:* planner
  - *Why:* Two failures in opposite directions. A reviewer sharing the implementer's context inherits its rationalizations: Cognition's Devin Review runs with 'completely clean context', catches ~2 bugs per PR of which ~58% are severe. Claude Code's continue-vs-spawn table routes 'verifying code a different worker just wrote' to spawn-fresh because 'verifier should see the code with fresh eyes.' The over-correction is equally documented: Anthropic best practices — 'A reviewer prompted to find gaps will usually report some, even when the work is sound, because that is what it was asked to do. Chasing every finding leads to over-engineering: extra abstraction layers, defensive code, and tests for cases that can't happen.' Cognition also flags orchestrator filtering as the load-bearing step: the clean-context reviewer does not know what the user asked for or what was deliberately deferred.
  - *Confidence:* well-established
  - *Concrete implication:* Planner file: 'Always spawn the reviewer fresh — never continue the implementer worker to review its own work, and never continue a worker whose first approach was wrong.' Ship the review dispatch as a template, adapted from Anthropic: 'Review the diff for <task> against PLAN.md. Check that every requirement is implemented, the listed edge cases have tests, and nothing outside the task's scope changed. Report gaps, not style preferences. Treat anything that does not affect correctness or a stated requirement as optional.' Plus: 'Filter reviewer findings against the plan and the user's intent before turning any of them into work.'
- **Restate load-bearing repo rules inline in every dispatch, and add a precedence clause stating that the task instructions supersede the implementer's own persona.**
  - *Applies to:* planner
  - *Why:* Two separate mechanisms. First, referenced documents get skipped: Claude Code's built-in Explore and Plan agents 'skip your CLAUDE.md files and the parent session's git status', with 'no frontmatter field or per-agent setting to change which agents skip them', and Anthropic's stated remedy is 'If a rule must reach the subagent, such as "ignore the vendor/ directory," restate it in the prompt you give Claude when delegating.' Second, and rarer: implementer agents carry their own persona prompts, and both Cline and Claude Code APPEND the role definition to the base prompt rather than replacing it, so conflicts are structurally guaranteed. Roo is the only source that resolves it, with a bullet in the delegation contract: 'A statement that these specific instructions supersede any conflicting general instructions the subtask's mode might have.'
  - *Confidence:* reasonable-consensus
  - *Concrete implication:* Planner file's dispatch template includes both: a `## Project Rules That Apply Here` block restating the specific load-bearing conventions inline (never 'follow CLAUDE.md'), and a closing line verbatim: 'These instructions supersede any conflicting general instruction in your own role definition. Do only the work described here.' Also pass forward resolved facts from completed tasks concretely ('the API returns lastActive as an ISO 8601 string') rather than pointing at the earlier task.
- **The plan artifact's section order is fixed: Context/why → recommended approach ONLY → changes grouped by component with per-file [NEW]/[MODIFY]/[DELETE] and paths → verification split into automated commands and manual → explicit assumptions and non-goals.**
  - *Applies to:* planner
  - *Why:* Claude Code and Codex converged on nearly the same four sections independently, which is the strongest signal in the whole corpus. Claude Code phase 4: 'Begin with a Context section: explain why this change is being made — the problem or need it addresses, what prompted it, and the intended outcome'; 'Include only your recommended approach, not all alternatives'; 'Include a verification section describing how to test the changes end-to-end.' Codex: 'Summary, Key Changes or Implementation Changes, Test Plan, and Assumptions' in 3-5 short sections. Antigravity adds the per-file change verbs with absolute path links plus dependency-first component ordering (which is what makes parallel-vs-sequential dispatch decidable straight from the plan) and 'If there are no such items, omit this section entirely.' The 'recommended approach only' rule matters most: a cold implementer treats alternatives-considered as live options and may pick a rejected branch.
  - *Confidence:* well-established
  - *Concrete implication:* Ship the plan template as a literal skeleton in the planner file with those headings in that order, per-file entries formatted `#### [MODIFY] src/auth/validate.ts`, components ordered dependencies-first, and the instruction 'Omit any section entirely when it is empty — do not write "None."' Add: 'Include only your recommended approach. Alternatives considered belong in your working notes, not in the plan the implementer reads.'
- **The planner classifies the work type before allocating, and states the classification in writing.**
  - *Applies to:* planner
  - *Why:* Anthropic's shipped lead prompt does not jump to delegation — it forces a labeled branch first (depth-first / breadth-first / straightforward) with 'Explicitly state your reasoning on what type of query this question is', and each branch gets a different allocation recipe. The coding analogue is a real distinction with opposite correct topologies: a hard debugging question is depth-first (competing hypotheses, parallel read-only investigators, single writer at the end) while a 40-file migration is breadth-first (partition by file, parallel writers on disjoint sets). Anthropic independently endorses the depth-first coding case in agent teams: 'Debugging with competing hypotheses: teammates test different theories in parallel.' Traycer routes on a different but complementary axis — remaining uncertainty rather than domain: 'If a file-level plan can be directly written, hand over to planner. If it requires more exploration, hand over to architect. If it requires multi-faceted analysis, hand over to engineering_team.'
  - *Confidence:* reasonable-consensus
  - *Concrete implication:* Planner file gets a mandatory first step: 'Before allocating any task, state in one sentence which shape this work is: (a) STRAIGHTFORWARD — one focused change, no fan-out, possibly no plan at all; (b) DEPTH-FIRST — one hard question with competing hypotheses; fan out read-only investigators in parallel, then ONE writer; (c) BREADTH-FIRST — independent components with clean interfaces; partition by file ownership and fan out writers. Justify the classification in the plan.'
- **Label facts in the plan by epistemic status: which file paths you actually opened versus which you inferred.**
  - *Applies to:* planner
  - *Why:* Magentic-One separates fact-gathering from plan-writing into two LLM calls and forces four mandatory headings — GIVEN OR VERIFIED FACTS / FACTS TO LOOK UP / FACTS TO DERIVE / EDUCATED GUESSES — closing the first with 'DO NOT list next steps or plans until asked to do so.' Ported to coding, this converts 'the plan hallucinated a file path' from a mystery into a labelled risk: steps built on a guess need a verification step, steps built on verified facts do not. It also complements the rule most conventionally placed in the implementer: Traycer duplicates 'NEVER assume that a given library is available, even if it is well known... first check that this codebase already uses the given library' into BOTH of its planning-only prompts, because a hallucinated dependency in a plan is worse than one in code — the implementer inherits it as an approved decision and installs it.
  - *Confidence:* single-source
  - *Concrete implication:* Plan template gets a `## Facts` section with two subheadings: `### Verified` (files I opened, commands I ran and their output, symbols I confirmed exist) and `### Inferred` (paths, conventions, or library availability I am assuming but did not confirm — each with how the implementer should check it). Planner file: 'Before naming any library or framework, confirm the repo already uses it by reading the manifest and a neighbouring file. Never assume availability from general knowledge.'
- **Give the implementer the whole plan for orientation but scope its mandate to exactly one task, tell it to act before exploring, and cap its exploration numerically.**
  - *Applies to:* implementer
  - *Why:* Seeing the full plan prevents over-scoping into later tasks' territory (it can see they are covered) while the single-task mandate prevents it from doing them. LangGraph renders the full numbered plan then appends 'You are tasked with executing step {1}.' CrewAI's step_executor is the sharpest version: 'You are executing ONE specific step in a larger plan. Your ONLY job is to fully complete this step — not to plan ahead. ACT FIRST. Execute the primary action of this step immediately. Do NOT read or explore files before attempting the main action unless exploration IS the step's goal... Do NOT spend more than 3 tool calls on exploration/analysis before attempting the primary action.' The numeric cap attacks the biggest implementer cost sink — re-deriving context the planner already established — and it only works because the plan names exact paths, which is why the two prompts must be designed together.
  - *Confidence:* reasonable-consensus
  - *Concrete implication:* Implementer file: 'You execute ONE task. The full plan is provided for orientation only — do not do work belonging to other tasks. Act first: if the task says "run X", run X now; if it says "edit file Y", open Y and edit it. Spend at most 3 tool calls on orientation before your first substantive action. If the plan named a path that does not exist, HALT and return OUTCOME: plan-is-wrong — do not go looking for the right one.'
- **Ban non-coding tasks from the plan with an enumerated denylist, and require the task sequence to end wired together with no orphaned code.**
  - *Applies to:* planner
  - *Why:* Planners reliably pad task lists with work the implementer structurally cannot perform, and the implementer then either fabricates completion or halts. Kiro's prompt enumerates the categories rather than saying 'only actionable tasks': user acceptance testing, deployment to production/staging, performance metrics gathering, 'running the application to test end to end flows' (automated E2E tests are fine), user training or documentation creation, business process changes, marketing. Separately, the classic planner failure is a task list that builds five components and never wires them: Kiro's counter is 'each prompt builds on the previous prompts, and ends with wiring things together. There should be no hanging or orphaned code that isn't integrated into a previous step' — which forces the planner to check reachability of everything it plans to create.
  - *Confidence:* single-source
  - *Concrete implication:* Planner file gets both lists verbatim: a denylist ('Never include tasks for: user acceptance testing, deployment to staging or production, gathering performance metrics in production, manually running the app end to end, writing user documentation or training, or business-process changes. Automated tests that exercise end-to-end behavior ARE allowed.') and the reachability rule ('Every artifact your plan creates must be reachable from an entry point by the last task. Before emitting, trace each new file and confirm a later task wires it in. No orphaned code.').
- **Have the implementer express changes by editing files in the repo; never have it hand a patch back as text.**
  - *Applies to:* implementer
  - *Why:* Largest single-decision effect measured anywhere in the sourced material. Same model, same tasks: an adapter that asked the model to output a unified diff in its final response scored 19.1% Pass@1 with a 69.1% apply-failure rate; the adapter that let the agent edit files under the checkout and had the runner export `git diff` scored 73.4% with under 1.5% apply failures. The stated cause: 'line numbers, context, hunk headers, or trailing newlines can make the patch fail to apply.' This generalizes to any handoff where a child must serialize a code change through a text channel — the same failure applies to a plan that asks for code blocks the planner will paste in.
  - *Confidence:* well-established
  - *Concrete implication:* Implementer file: 'Apply your changes with file-editing tools directly in the working tree. Never return a diff, patch, or code block for someone else to apply — report the paths you edited and let the harness read the diff from git.' Planner file mirror: 'Never ask a worker to return code for you to apply. Ask it to edit the files and report the paths and the commit hash.'
- **Route the model per role, and let the planner set the implementer's model from a difficulty field in the plan rather than hardcoding it.**
  - *Applies to:* both
  - *Why:* Planning is the step where a wrong decision propagates into every downstream task, so it is the step most worth paying for; mechanical implementation and read-only exploration are the steps most worth capping. Anthropic ships `model` as a first-class frontmatter field and names cost control as a benefit ('Control costs by routing tasks to faster, cheaper models like Haiku'), with the SDK example encoding `model: isStrict ? "opus" : "sonnet"` and the comment 'use a more capable model for high-stakes reviews.' wshobson's 203-agent marketplace routes every architect-class agent to opus and language implementers to sonnet. handoff-kit goes further and reads the model from the plan itself, because the planner is the only agent that has actually read the code and knows whether a step is mechanical or subtle. Counter-note worth flagging: Anthropic's own coordinator prompt says 'Do not set the model parameter' for its generic workers.
  - *Confidence:* reasonable-consensus
  - *Concrete implication:* Planner frontmatter uses the strongest model with high effort; implementer frontmatter uses the default. Plan template gives each task a `difficulty: 1-10` and `model:` field, and the planner file says: 'Set difficulty per task from how much judgment it needs, not how much typing. Route 8-10 to the strongest model at high effort, 4-7 to the strongest model at medium, 1-3 to the cheaper model.' Orchestrator section: 'Read the difficulty/model fields from the plan and pass the model at spawn time; do not rely on the implementer's frontmatter default.'
- **Write the `description` frontmatter field as a trigger condition, not a capability blurb — it is the only thing the parent reads when deciding to delegate.**
  - *Applies to:* both
  - *Why:* Every framework surveyed separates 'what the parent reads to choose you' from 'what you read to do the job', and composes the former into the delegation tool's schema automatically. Anthropic: 'Claude uses each subagent's description to decide when to delegate tasks', and 'To encourage proactive delegation, include phrases like "use proactively".' Google ADK is blunt: 'the description field of your sub-agents is effectively your API documentation for the LLM. Be precise.' The SDK lists a vague description as one of three named causes of 'Claude not delegating to subagents.' The practical consequence: if the planner keeps picking the wrong implementer, the fix is in the description, not in more routing rules in the planner's body — and descriptions should be short because they sit in the parent's context permanently.
  - *Confidence:* well-established
  - *Concrete implication:* Both descriptions are when-clauses with a negative half: planner — 'Use when a code change spans more than one file or needs decisions made before implementation begins. Produces a decision-complete implementation plan at <PLAN_PATH>. Do NOT use for single-file changes or read-only questions.' Implementer — 'Use to execute exactly one task from an existing implementation plan. Requires the plan path and the task ID. Do NOT use without a plan.'
- **Budget rounds, stalls, and replans as three separate counters with different consequences — not one 'max iterations'.**
  - *Applies to:* planner
  - *Why:* They terminate differently and collapsing them loses the only recovery path that works. Microsoft Agent Framework ships production defaults `max_round_count=10, max_stall_count=3, max_reset_count=2`; AutoGen separates `_max_turns` (→ answer with what you have) from `_max_stalls` (→ rewrite the plan) from `_max_json_retries` (→ parse). Hitting max rounds means stop and report; max stalls means the plan is wrong, replan; max resets means escalate to a human. Magentic-One additionally makes the stall counter hysteretic — `n_stalls = max(0, n_stalls - 1)` on progress rather than resetting to zero — so a run alternating progress/stall never runs forever and a long healthy run is not tripped by two unlucky rounds. And it updates the fact ledger BEFORE clearing the transcript, so the replan is conditioned on what was learned rather than starting from nothing.
  - *Confidence:* reasonable-consensus
  - *Concrete implication:* Planner file: 'Track three counters separately. ROUNDS (dispatch cycles, max 10): on limit, stop and report completed vs remaining. STALLS (cycles with no verified artifact change, max 3; decrement by one on a verified advance, floor 0): on limit, write the root cause into the plan and replan the remaining tasks. REPLANS (max 2): on limit, halt and escalate to the human with the blocker. Before any replan, write what you learned into the plan\'s Facts section — never replan from an empty slate.'
- **Gate replanning behind concrete triggers, and revise only the remaining tasks — never rewrite the whole plan on a surprise.**
  - *Applies to:* planner
  - *Why:* Unconstrained replanning is how orchestrators burn budget without converging: every surprising observation looks like a reason to rewrite. CrewAI gates it: 'Be conservative about triggering full replans — only do so when the remaining plan is fundamentally wrong, not just suboptimal', followed by a mechanically checkable trigger: 'Set needs_full_replan=true if the current plan's remaining steps reference paths or state that don't exist yet and need to be created first.' The complementary rule appears in two independent framework replanner prompts: LangGraph 'Only add steps to the plan that still NEED to be done. Do not return previously done steps'; LLMCompiler 'In the Current Plan, you should NEVER repeat the actions that are already executed' and 'You must continue the task index from the end of the previous one', with the next index computed in code and injected rather than left to the model. Step Repetition is MAST's largest single failure mode at 15.7–17.1%.
  - *Confidence:* reasonable-consensus
  - *Concrete implication:* Planner file: 'Replan only when the REMAINING tasks are fundamentally wrong, not merely suboptimal. Concrete triggers: a remaining task references a path or symbol that an earlier task was supposed to create and did not; an implementer returned plan-is-wrong with evidence; the stall counter hit its limit. On replan: keep every completed task exactly as written, append new tasks continuing the ID sequence from the highest existing ID, and never reuse or renumber an ID.'
- **Before adopting the pair, measure a single-agent control arm on the same tasks — and size the number of runs from a power table, not convenience.**
  - *Applies to:* both
  - *Why:* Coordination is not monotonic and reading the prompts cannot tell you which way it goes. Harness/agent-definition choice at a fixed model moved Pass@1 by 12.5pp on one model and 27.4pp on another — 'large enough to reorder leaderboard conclusions.' Controlled scaling work reports outcomes from +80.8% to -70.0% depending on task shape. Anthropic itself says 'most coding tasks involve fewer truly parallelizable tasks than research, and LLM agents are not yet great at coordinating', and warns teams have 'invest[ed] months building elaborate multi-agent architectures only to discover that improved prompting on a single agent achieved equivalent results.' Meanwhile identical configs vary 2.2–6.0pp run to run even at temperature 0, so one run per arm only supports a ~10pp claim; ~9 runs per arm supports 2pp. And the realistic ceiling for a prompt rewrite is single-digit to mid-teens points — MAST's best structural intervention was +15.6%, best prompt-level was +9.4%.
  - *Confidence:* well-established
  - *Concrete implication:* Ship the pair with a checked-in golden task set (8–10 tasks per role, 60–70% currently passing so regressions are detectable) and a mandatory single-agent control arm running the same tasks with the same model and timeout. Record Pass@1, total tokens, and wall-clock in one table; adopt only on the Pareto frontier. Write the chosen repeat count and the effect size it supports into the eval README. Add deterministic control-plane assertions first — that the Agent tool fired, that subagent_type matched, that the tool subset held — before any LLM judging.

## Antipatterns

- **Splitting one unit of work into planner-agent → implementer-agent → tester-agent → reviewer-agent as four parallel roles.**
  - *Failure mode:* Anthropic names it 'problem-centric decomposition (often counterproductive)' and reports these setups 'spent more tokens on coordination than on actual work'; the phases 'share too much context', producing 'a telephone game where context degrades at each handoff.' Coordination tokens exceed work tokens and correctness drops versus one thread with written artifacts.
  - *Guard:* Planner file: 'Never create separate tasks for planning, implementing, testing, and reviewing the same change. Those are stages of ONE task with written artifacts. Split only along independent file/module boundaries with clean interfaces.' The planner→implementer pair itself is a sequential two-stage thread with a durable artifact between them — not a role split — and the agent files must say so.
- **Two implementers assigned overlapping files, or a [P] marker assigned by intuition.**
  - *Failure mode:* Last write wins with no merge arbitration; the orchestrator sees two successful summaries and never learns work was lost. Cognition's Flappy Bird case: both outputs individually plausible, jointly incoherent, and no automated check catches it.
  - *Guard:* Define [P] mechanically in the planner file: 'two tasks may run in parallel only if their owned-file sets are disjoint — intersect the sets and drop the marker if they overlap.' Each task lists `owns:` paths and the implementer is told 'never edit a file outside your task\'s owns list; if you must, HALT and return plan-is-wrong.' Where available, set `isolation: worktree`.
- **Enforcing planner read-only in prose ('you must not edit files') or via a mode flag rather than the tool grant.**
  - *Failure mode:* MAST FM-1.2 Disobey Role Specification: role boundaries stated only in prose leak under pressure, especially right after the user types something imperative. The plan then reflects work already half-done and the human approves a plan whose premises were silently mutated. Claude Code's own docs note that in sessions with bypassPermissions/acceptEdits/auto, plan mode's blocks are not enforced and a `permissionMode: plan` on a subagent is ignored entirely.
  - *Guard:* Frontmatter `tools:` allowlist (or `disallowedTools: Write, Edit, NotebookEdit`) scoped so the plan path is the only writable target. Never rely on `permissionMode: plan` as the guarantee. Keep the prose prohibition too, as a second layer — Claude Code and Codex both ship both.
- **A prose plan: 'refactor the auth middleware to use the new token store', no paths, no symbols, no commands.**
  - *Failure mode:* The implementer starts cold, re-derives the file set by guessing, lands in the wrong module or duplicates an existing helper. HKUST calls it context fragmentation and it is one of the two root mechanisms behind their 700+ analyzed failures.
  - *Guard:* Plan template forbids a task line without a repo-relative path; the planner file ships four ❌ examples each missing exactly one required component. Implementer file: 'return bad-dispatch and name the unresolvable reference rather than guessing.'
- **'Handle the edge cases' / 'be careful with boundary conditions' with no stated correct behavior.**
  - *Failure mode:* 41.6% of planner-coder gap failures (EP-2 19.5% + EP-5 22.1%). The coder acknowledges the edge case in a comment and implements nothing, or implements the opposite. The plan reviews as thorough and the code is wrong.
  - *Guard:* Plan template requires every edge case as `<condition> → <expected behavior>`. The planner file bans the bare form by name. The implementer file requires restating three concrete edge cases with their handling BEFORE writing code.
- **Reusing the user's ambiguous domain vocabulary in the plan without defining it.**
  - *Failure mode:* EP-1, 32.7% of gap failures — the largest single sub-category. 'Remove all duplicates' becomes dedupe-keeping-one instead of delete-every-repeated-element. Planner and coder are each individually correct; the meaning is lost at the boundary.
  - *Guard:* Required `## Operational Definitions` section: 'For each key term in the requirement, state exactly what it means in code terms before using it in a step.'
- **Letting raw subagent transcripts and tool output flow back into the planner's context.**
  - *Failure mode:* Blows the planner's window around step 4-6 and degrades before it blows — context rot shows non-uniform accuracy loss with input length across all 18 models tested, and stale intermediate output acts as distractors that measurably increase hallucination. You paid 4–6x tokens for the same context pollution you were avoiding.
  - *Guard:* Implementer file caps its report (300–800 words, fixed sections). Planner file: 'Never paste raw worker output into a follow-up dispatch — synthesize.' Where the harness supports it, use last-message-only or a bounded preview.
- **Truncating to the implementer's last message without telling the implementer that is all the parent sees.**
  - *Failure mode:* Implementers write 'Done — see the analysis above', and 'above' is exactly what got dropped. The planner now holds a completion claim with no content (MAST FM-2.4 Information Withholding).
  - *Guard:* deepagents' one sentence, near the top of the implementer file: 'The calling agent only sees your final assistant message, not your intermediate work, tool results, or status tracking. Ensure your final response contains the complete answer.'
- **Accepting the implementer's word that a step succeeded.**
  - *Failure mode:* MAST Reasoning-Action Mismatch (13.98%) + No/Incomplete Verification (6.82%) ≈ a fifth of all observed failures. A verifier prompted vaguely 'marks outputs as passing without thorough testing' — a ChatDev chess program compiled and passed review while violating the rules of chess.
  - *Guard:* Planner-side acceptance checklist with enumerated disqualifiers (exploratory-only output, unexplained non-zero exit, create/build/start step with no matching artifact) plus a `git diff <base_sha>..` check on the files the task owned. Reviewer dispatch names the literal command and a binary pass condition: 'Run: <cmd>. Only mark PASSED if it exits 0 with no failures. Do not mark passing after running a subset.'
- **A reviewer told only to 'find gaps'.**
  - *Failure mode:* 'A reviewer prompted to find gaps will usually report some, even when the work is sound, because that is what it was asked to do. Chasing every finding leads to over-engineering: extra abstraction layers, defensive code, and tests for cases that can't happen.'
  - *Guard:* Review dispatch closes with 'Report gaps, not style preferences. Treat anything that does not affect correctness or a stated requirement as optional.' Planner filters findings against the plan and user intent before any becomes work.
- **One plan.md that both planner and implementer write.**
  - *Failure mode:* The implementer edits the plan to match what it did, so the plan stops being a spec and becomes a changelog. Review against the plan becomes vacuous — the diff always matches — and there is no way left to detect that the plan itself was wrong. HN practitioners report LLMs 'modifying acceptance criteria to make implementations pass artificially.'
  - *Guard:* Split by writer: PLAN.md (planner-only), PROGRESS.md (implementer checkboxes + log), DECISIONS.md (implementer appends deviations and questions). Implementer file: 'You may never edit PLAN.md.' Where the harness supports path scoping, enforce it.
- **Emitting plan-v2.md on revision, or rewriting/renumbering/reordering existing tasks.**
  - *Failure mode:* The dispatch prompt, the implementer's cached path, and the human's open tab point at different generations; nothing is authoritative and the disagreement is undetectable. Renumbering silently invalidates any in-flight implementer holding older task IDs.
  - *Guard:* Planner file: 'On revision, overwrite the SAME path. Append new tasks in a new numbered phase continuing the ID sequence. Never rewrite, renumber, reorder, or delete an existing task, including tasks from a prior revision phase. If nothing needs to change, leave the file byte-for-byte unchanged.'
- **Implementer starts editing without reconciling the plan against the working tree.**
  - *Failure mode:* Builds on a stale map when the plan was authored hours ago or partially executed. Redoes completed steps, or skips steps whose checkboxes were ticked but whose code never landed. Checkpoints do not save you — subagent edits and Bash-driven mutations are outside checkpoint scope.
  - *Guard:* Mandatory step 1 in the implementer file: read the artifacts, run `git status --porcelain` / `git log --oneline -10` / `git diff --stat`, compare the plan's recorded base SHA against HEAD, and HALT with `stale-plan` on any inconsistency.
- **Re-dispatching a fresh implementer onto the same task after a blocked or partial return.**
  - *Failure mode:* The new implementer starts cold with no knowledge of the files already edited. On a non-idempotent change (adding an import, appending a switch case, bumping a version) it double-applies, and the second run's report looks clean.
  - *Guard:* Planner dispatch table routes blocked-on-decision to RESUME the same worker by its agent ID, and routes partially-applied to a git-state check plus an explicit '## Already Built' list in the re-dispatch, or a revert to base SHA first. Never re-dispatch cold onto an unverified tree.
- **No numeric fan-out rule — leaving worker count to model judgment.**
  - *Failure mode:* Anthropic's own system was 'spawning 50 subagents for simple queries.' The inverse is also documented: a lead that creates too few tasks and leaves workers idle. Over-decomposition also multiplies the number of lossy boundaries, and each boundary is another chance for the 74% planner-coder information loss.
  - *Guard:* Literal ladder plus a ceiling in the planner file, plus the tie-breaker: 'Prefer fewer, more capable tasks over many narrow ones. Only add a task when it provides distinct value.'
- **No don't-orchestrate branch — planning and delegating a change that fits in one sentence.**
  - *Failure mode:* You pay a cold start, a CLAUDE.md reload, re-discovery of files the planner already read, and 4–6x tokens with a measured latency regression, for work that took one tool call. Anthropic: 'If you could describe the diff in one sentence, skip the plan.'
  - *Guard:* Planner file opens with the branch: 'If the change is describable in one sentence, or fits in under 3 steps, or is a read-only question, say so and return without a plan. Latency and token cost of this pair are only justified by genuinely independent work.'
- **Task lines that build components with no wiring step, or that include unexecutable work (deploy to staging, gather user feedback).**
  - *Failure mode:* Everything compiles, all boxes are checked, nothing is reachable. And an implementer handed a task it structurally cannot perform either fabricates completion or halts.
  - *Guard:* Kiro's two rules verbatim in the planner file: the enumerated non-coding denylist, and 'each task builds on the previous and the sequence ends with wiring things together. There should be no hanging or orphaned code that isn't integrated into a previous step.'
- **Padding the plan with 'review', 'document', 'finalize' steps that produce no artifact.**
  - *Failure mode:* Burns rounds producing narration instead of change, and pollutes the DONE-criterion signal because such steps always succeed. CrewAI bans them by name.
  - *Guard:* Planner file: 'Every task must produce a checkable artifact or a command exit code. Running the test suite or a build IS a real task; "review the results" is not. The test is whether a machine can tell the difference between done and not done.'
- **Using angle-bracket pseudo-XML (<result>, <status>) as the return-envelope delimiter, or echoing transcript-shaped lines.**
  - *Failure mode:* The harness scans subagent output and mutates control-tag-shaped text — inserting a backslash after the opening angle bracket, backslashing line-leading `Human:`/`Assistant:`, and prepending a `[harness: ...]` marker. A strict parser then fails exactly on the reports that quote logs or code, i.e. the informative ones.
  - *Guard:* Implementer file mandates a fenced ```handoff block whose first line is `OUTCOME: <token>`. Planner-side parsing tolerates a prepended `[harness: ...]` line and treats an unparseable envelope as UNKNOWN routed to verification, never to accept.
- **Treating the Agent tool result as necessarily authored by the implementer.**
  - *Failure mode:* Three of the shapes the planner can receive are written by the harness: truncated partial output with a cutoff note, the literal 'Agent terminated early due to an API error', and a background-failure message with last output attached. An API cutoff after three of seven edits produces prose that reads like a progress report; a planner pattern-matching 'looks like a report' marks the step done over a half-edited repo.
  - *Guard:* Planner file: 'Absence of a parseable OUTCOME line means UNKNOWN. Route UNKNOWN through the same git-state verification as partially-applied. Never accept a step whose report you did not parse.'
- **Letting the implementer fix unrelated issues it notices, or run `git add .`.**
  - *Failure mode:* Task derailment (MAST FM-2.3, 7.4%) plus unreviewable diffs — the plan-conformance review can no longer tell what was in scope.
  - *Guard:* Claude Code's worker rules verbatim in the implementer file: 'Do not fix unrelated issues you discover — record them as follow-ups in your report. Do not use `git add .` or blanket staging. Do not retry identical failed approaches. Do not modify code you don\'t understand.'
- **Presenting alternatives-considered in the plan handed to the implementer.**
  - *Failure mode:* A cold implementer treats the alternatives as live options and may build a rejected branch. Reads as sophistication, functions as ambiguity.
  - *Guard:* Planner file: 'Include only your recommended approach, not all alternatives.' Alternatives belong in working notes or a research artifact, not the handoff.
- **Referencing project rules ('follow CLAUDE.md', 'see the style guide') in the dispatch instead of restating the load-bearing ones inline.**
  - *Failure mode:* Referenced documents get skipped or skimmed. Structurally, some built-in agents skip CLAUDE.md entirely with no setting to change it, and no subagent inherits the parent's conversation, output style, or auto-memory.
  - *Guard:* Dispatch template includes a `## Project Rules That Apply Here` block restating the specific conventions inline, plus a precedence line: 'These instructions supersede any conflicting general instruction in your own role definition.'
- **Responding to an observed failure by appending more emphatic instructions to the planner prompt.**
  - *Failure mode:* Measured low ceiling: MAST's best prompt-level intervention was +9.4% versus +15.6% for a structural one (adding a verification stage), and 'task completion rates still remain low.' Prompt inflation also directly costs context budget.
  - *Guard:* Team rule stated in the repo, not the prompt: 'Before adding a paragraph to an agent file, ask whether the fix is structural — a tool restriction, a required plan section, a verification stage, or a topology change. Prefer the structural fix.'
- **Adding the pair without measuring a single-agent control, or declaring victory from one run per arm.**
  - *Failure mode:* Coordination is not monotonic (+80.8% to -70.0% depending on task shape) and identical configs vary 2.2–6.0pp run to run, so any claimed improvement under ~10pp from a single run is indistinguishable from a reroll. You ship a prompt edit that did nothing and then defend it.
  - *Guard:* Golden task set plus a mandatory control arm checked in beside the agent files; the chosen repeat count and the effect size it supports written into the eval README; cost and wall-clock reported in the same table as pass rate.

## Handoff contract

### Plan sections

- Header / frontmatter — plan id or slug, `base_sha:` recorded before dispatch, status (draft | approved | in-progress | done), and per-task `difficulty: 1-10` + `model:` routing fields the orchestrator reads at spawn time.
- ## Context — why this change is being made: the problem or need, what prompted it, the intended outcome. First section, always present. (Claude Code phase-4 + Codex converge on this.)
- ## Non-goals / Out of scope — explicit. Prevents the implementer's scope creep from looking like initiative.
- ## Assumptions & Open Decisions — every preference decision the planner made silently, stated as a decision. Unresolved items appear inline as grep-able `[NEEDS CLARIFICATION: <question>]`; a plan containing one is not ready to hand off.
- ## Operational Definitions — every domain term the plan uses, defined in code terms. Targets the 32.7% EP-1 failure class.
- ## Facts — split `### Verified` (files actually opened, commands actually run with their output, symbols confirmed to exist) and `### Inferred` (paths, conventions, library availability assumed but unconfirmed, each with how to check it). Ported from Magentic-One's epistemic-status ledger.
- ## Files Being Modified — one entry per [MODIFY] file with three fields: Current state / This change / Must preserve. BMAD names skipping this as the primary cause of implementation failures.
- ## Proposed Changes — grouped by component, ordered dependencies-first, each file tagged `#### [NEW] | [MODIFY] | [DELETE] <repo-relative path>`. Recommended approach only, no alternatives. Prescriptive about interfaces, contracts, and boundaries; permissive about internals. For patterns repeated across many files, describe the pattern once and list 3-5 representative paths — never enumerate every file or line number.
- ## Tasks — one line each: `- [ ] T### [P] [REQ-ref] <verb-led ≤14-word description> in <path>`. Per task, a nested block with: `owns:` (exclusive file list), `depends-on:` (task IDs), `edge-cases:` (each as `<condition> → <expected behavior>`), `produces:` (the artifact), `DONE:` (exact command), `EXPECT:` (exit 0 / named assertion). `[P]` means owned-file sets are disjoint — verified by intersection, not judgment. Hard cap of 10 tasks.
- ## Verification Plan — `### Automated` (exact commands with exit-0 expectations) and `### Manual`, plus ONE end-to-end check that proves the feature works as a user would experience it.
- ## Rollback — how to undo, and the blast radius if a task lands partially.
- (Empty sections are omitted entirely — never written as 'None.')

### Report sections

- `OUTCOME: <token>` as the first line of a fenced ```handoff block. Token ∈ {done, done-with-deviations, blocked-on-decision, plan-is-wrong, partially-applied, bad-dispatch}. Never angle-bracket delimiters.
- `task_id:` — the exact task ID from the plan.
- `files_written:` — repo-relative paths actually created or edited, one per line. Must be a subset of the task's `owns:` list.
- `base_sha:` / `head_sha:` / `git_status:` — the recorded base, the current HEAD, and the raw `git status --porcelain` output. This is the planner's ground truth, not the prose.
- `verification:` — the exact DONE command run, its exit code, and the last ~20 lines of its output pasted verbatim. Not a claim that it passed.
- `deviations:` — anything done differently from the plan, and why. Empty is the expected value.
- `blockers:` — questions requiring a planner decision, each stated as a question with the options the implementer sees. Only present on blocked-on-decision.
- `unrequested_changes:` — anything touched outside the task's scope. Should always be empty; a non-empty value is a defect regardless of outcome.
- `follow_ups:` — issues noticed but deliberately not fixed. Records them without acting on them.
- `summary:` — one sentence in the shape 'Added Redis cache implementation. Tests pass, typecheck clean. Committed abc123.' The whole report must be self-contained (300-800 words): the planner sees this final message and nothing else.

### Failure signaling

Six outcomes, each mapping to a DIFFERENT planner action — merge any two that would produce the same action. (a) `done` → verify by artifact and exit code, then advance. (b) `done-with-deviations` → read DECISIONS.md, decide accept-or-revert, then advance; a deviation is never silently accepted. (c) `blocked-on-decision` → the planner answers and RESUMES the same worker by its agent id; never re-dispatch cold, because a cold retry double-applies non-idempotent edits onto a half-edited tree. (d) `plan-is-wrong` → append remediation tasks with fresh IDs continuing the sequence; never rewrite completed tasks; increment the replan counter. (e) `partially-applied` → run `git diff <base_sha>..`, decide revert-or-continue, and if continuing, re-dispatch with an explicit '## Already Built' list of the files that exist. (f) `bad-dispatch` → rewrite the dispatch and re-send; this is the only outcome with zero repo state to reconcile. Plus one class the implementer cannot emit: absence of a parseable OUTCOME line means UNKNOWN (harness cutoff, API error, crashed worker) and routes to the same git-state verification as partially-applied — never to accept. The implementer reaches these states via explicit HALT conditions: new dependency not in the plan, three consecutive failures on the same step, missing required file or config, ambiguity surviving a re-read of the plan, or needing to edit a file another task owns. Counters are separate and consequences differ: ROUNDS max 10 → stop and report; STALLS max 3, hysteretic (decrement on a verified advance, floor 0) → write root cause into the plan's Facts section, then replan the remaining tasks only; REPLANS max 2 → halt and escalate to the human with the blocker. The plan is always the authority: when plan and observed state disagree, the derived thing is regenerated and the divergence is appended to DECISIONS.md. The implementer never edits PLAN.md to match what it did.

## Structural conventions

- YAML frontmatter is where enforcement lives; the body never restricts anything. Convergent field set across Claude Code, Roo, VoltAgent, wshobson, and GitHub's copilot spec: `name`, `description`, `tools` (allowlist) or `disallowedTools`, `model`. Claude Code adds `permissionMode`, `isolation`, `maxTurns`, `skills`, `memory`, `effort`. Roo expresses the same idea as `groups: [read, [edit, {fileRegex}], mcp]`. If a rule matters, it belongs in frontmatter, not a paragraph.
- `description` is a routing string, not a bio — it is the only text the parent reads when choosing to delegate. House style is a when-clause: VoltAgent normalizes on `Use when <trigger condition>.`; wshobson on `<capability sentence>. Use PROACTIVELY for <trigger>.` Good descriptions also carry a negative half ('Do NOT use for single-file changes'). They sit in the parent's context permanently, so keep them to two sentences.
- Body section order is near-identical everywhere: (a) one-line identity in second person present — 'You are X specializing in Y'; (b) a `When invoked:` numbered 1-4 boot sequence; (c) a domain checklist; (d) constraints/limits; (e) an output-format section; (f) sometimes 'Integration with other agents'. The serious planner prompts (Roo, Traycer, Antigravity, Codex) add an explicit `<limitations>` or read-only clause that marketplace files omit.
- Imperative mood is codified, not stylistic. GitHub's authoring spec: 'Specific and Direct: Use imperative mood ("Analyze", "Generate"); avoid vague terms.'
- XML-ish tag sectioning (`<role>`, `<limitations>`, `<decision_tree>`, `<critical>`, `<important>`) dominates the closed-source production prompts (Traycer, Antigravity, Cursor, BMAD); markdown `##` headers dominate open marketplace files. The tagged style reads noticeably tighter and more rule-like — but note the harness may rewrite angle-bracket text in SUBAGENT OUTPUT, so use tags for prompt structure, never for the return envelope.
- Rules are stated as enumerations of forbidden specifics, not as general principles. Claude Code plan mode enumerates 'Creating new files… Modifying existing files… Deleting files… Moving or copying files… redirect operators (>, >>, |) or heredocs'. Kiro enumerates the seven categories of non-coding task. Spec Kit ships four ❌ WRONG task lines each missing exactly one component. The coordinator prompt bans the literal strings 'based on your findings' and 'based on the research'. Naming the specific violation is consistently more effective than describing the class.
- Worked ✅/❌ pairs, side by side, are the dominant teaching device for anything format-shaped — task lines (Spec Kit), delegation prompts (Claude Code coordinator), plan sections (Antigravity). Ship the wrong version, not just the right one.
- Numbers, not adjectives, wherever behavior needs bounding: '≤14 words', 'at least 5 minutes of user work', '3-5 critical files', 'no more than 3 tool calls on exploration', '3 consecutive failures', 'MAX_ITERATIONS=8', 'max_stall_count=3', 'Never create more than 20 subagents'. Every source that bounds something bounds it numerically.
- 'Your final message IS the deliverable' framing appears in three forms and is load-bearing in all of them: Roo's 'this summary will be the source of truth used to keep track of what was completed on this project'; deepagents' 'The calling agent only sees your final assistant message'; GitHub copilot's 'Return a clear summary (actions taken + files produced/modified + issues)'. Telling the model the epistemic status of its own output changes what it puts there.
- Output contracts are increasingly named artifacts on disk rather than message shapes — Antigravity's `implementation_plan.md` / `task.md` / `walkthrough.md`, Roo's `/plans`, Spec Kit's spec.md/plan.md/tasks.md, BMAD's story file with reserved write-back sections. This is the clearest 2025→2026 trend, and it comes with per-writer write-scoping.
- A near-universal tail block: an ALL-CAPS re-assertion of the one rule most likely to be violated. 'REMEMBER: You can ONLY explore and plan.' 'CRITICAL: Never provide level of effort time estimates.' 'NEVER mark a task complete unless ALL conditions are met - NO LYING OR CHEATING.' 'NOTE: You must use one of the provided tools… TEXT only response is strictly prohibited.' Repetition at the end is treated as load-bearing, not redundant.
- Delegation contracts are written as a fixed enumerated checklist inside the parent's prompt, not left to improvisation. Anthropic's seven items (objective / output format / background / key questions / starting points / tools / scope boundaries) and Roo's five bullets (context / scope / no-deviation clause / completion signal + summary shape / supersession clause) are the two canonical forms. Put the checklist in the delegation TOOL DESCRIPTION where the harness allows it — CrewAI and deepagents both do, so it is re-read immediately before every dispatch rather than sitting in a system prompt the model has drifted from.
- Decision tables beat prose for orchestrator branching. Claude Code's four-row continue-vs-spawn table and Traycer's three-line routing tiers are directly transplantable; the equivalent prose ('use fresh context when appropriate') is not executable.
- Anti-patterns are documented in the file itself, with the failure named. Claude Code's coordinator ships side-by-side anti-pattern and good-pattern tool calls; Spec Kit ships an `Avoid:` list ('vague tasks, same file conflicts, cross-story dependencies that break independence'). Marketplace files that omit this are the ones whose bodies constrain nothing.

## Contested

- MULTI-AGENT ITSELF — Cognition ('Don't Build Multi-Agents', Jun 2025: context fragmentation, implicit-decision conflict, single-threaded linear agents) versus Anthropic's orchestrator-worker research system. RESOLUTION, because both camps have since converged and the axes are real: (1) READ vs WRITE — fan out read-only investigation freely (Cognition 2026 calls read-only subagents 'mostly resemble tool calls'; LangChain: 'read actions are inherently more parallelizable'), serialize writes to one owner per file. (2) BOUNDARY vs PHASE — split along independent modules with clean interfaces, never along lifecycle phases of one feature (Anthropic 2026 says this explicitly, agreeing with Cognition). (3) SEQUENTIAL STAGES ARE NOT A ROLE SPLIT — a planner→implementer thread with a durable written artifact between them is not what either camp is arguing against; what both reject is parallel writers and role-decomposition of one unit of work. Usable rule for the agent files: 'One writer at a time per file. Parallel investigation, serial implementation. If two tasks would touch the same file, they are one task.'
- FILE-PATH SPECIFICITY IN PLANS — GitHub Spec Kit makes a missing file path a format ERROR ('- [ ] T001 [US1] Create model' is listed ❌ WRONG explicitly for 'missing file path'), while OpenAI Codex says the opposite: 'Prefer grouped implementation bullets by subsystem over file-by-file inventories… avoid naming more than 3 paths unless extra specificity is necessary.' RESOLUTION: the axis is whether the implementer starts cold. Spec Kit spawns a fresh agent per task, so paths are load-bearing; Codex's plan is consumed in the same session, so paths are noise. Since this pair uses cold implementers, side with Spec Kit — but adopt Claude Code's compromise for repeated changes: 'describe the pattern once and list a few representative paths — do not enumerate every file or line number.'
- VERIFICATION STEPS IN THE TASK LIST — CrewAI bans them ('NO standalone "thinking" or "planning" steps'; its reasoning prompt adds 'Do NOT pad with unnecessary steps like "review", "verify", "document", or "finalize"') while LangChain deepagents' coding planning skill requires them ('Include test writing and test running as explicit steps'; 'End with a review/verification step'). RESOLUTION: the discriminator is whether the step produces a checkable artifact or exit code. 'Run pytest -q' is a real action with a binary outcome; 'review the results' is narration. Side with deepagents for coding, and encode CrewAI's concern as the artifact test rather than a ban.
- WHO TICKS THE CHECKBOX — rails_ai_agents is emphatic that the parent owns it ('the parent owns all file tracking, not the subagent'; 'This is always done by the parent, not by subagents') while SIRHAMY's orchestrator tells the subagent to 'Mark each task complete (- [x]) as you finish it' and handoff-kit sides with the implementer ('After every meaningful change, update PROGRESS.md'). No source found argues for one over the other. Parent-owned gives a single writer and survives subagent failure mid-task; implementer-owned gives finer granularity and survives orchestrator compaction. Pick one and state it in BOTH files — if they disagree you get double-ticking or a plan that never advances.
- IMPLEMENTER STOP CADENCE — Kiro's task-execution prompt: 'Only focus on ONE task at a time… Once you complete the requested task, stop and let the user review. DO NOT just proceed to the next task in the list.' BMAD's dev-story: 'Absolutely DO NOT stop because of "milestones", "significant progress", or "session boundaries"' and run to completion. These produce very different human-in-the-loop economics. RESOLUTION for a cold-context implementer spawned per task: Kiro's model is already enforced by the spawn boundary, so adopt BMAD's rule WITHIN a task ('finish this task or hit a HALT condition; do not stop at a narrative boundary') and Kiro's rule ACROSS tasks (the implementer never advances to the next task itself — the planner dispatches it).
- PRESCRIPTIVENESS OF THE PLAN — 'name exact paths and symbols' (Spec Kit, Devin, Antigravity, Traycer, Anthropic's cold-context argument) versus Cognition's production finding that managers become 'overly prescriptive, which backfires when the manager lacks deep codebase context', with the implementer — which does have the files open — following the wrong instruction anyway because the plan was approved. RESOLUTION: specificity about WHAT and WHERE (files, interfaces, contracts, acceptance checks, boundaries), latitude about HOW (internal implementation). Reinforce it by requiring the planner to actually read every file it marks [MODIFY], so its prescriptions are grounded rather than inferred.
- HOW MUCH CONTEXT TRAVELS IN THE DISPATCH — GitHub's own copilot authoring spec says the orchestrator 'passes only the essential context (e.g., base path, identifiers) and requires each sub-agent to read its own .agent.md spec', while CrewAI, deepagents, Roo, Anthropic, and Claude Code all say the opposite ('share absolutely everything you know, don't reference things but instead explain them'). RESOLUTION: side against GitHub here — delegating context acquisition to the subagent is the lossy handoff every failure study identifies, and referenced documents are exactly what practitioners report getting skipped. But adopt the hybrid the gap-fill found in production: pointer plus task-scoped projection, not the whole plan inlined and not a bare path.
- EXPLORE-BEFORE-PLANNING — Kiro's requirements prompt: 'Don't focus on code exploration in this phase. Instead, just focus on writing requirements which will later be turned into a design.' Codex mandates the reverse: at least one targeted non-mutating exploration pass before asking the user anything. RESOLUTION: these produce different artifacts. Kiro's phase-1 output is a behavior contract, where premature code reading smuggles the existing implementation into the acceptance criteria. This pair's planner produces an implementation plan, so Codex's rule applies: explore first, and never ask the user what the repo can answer.
- DOES THE PAIR HELP AT ALL — the whole planner/implementer industry versus controlled scaling work reporting outcomes from +80.8% to -70.0% by task shape, Stanford's matched-thinking-token result that single agents match or beat five MAS variants on multi-hop reasoning, and Anthropic's own line that 'most coding tasks involve fewer truly parallelizable tasks than research.' RESOLUTION: not resolvable by argument — it is an empirical question about YOUR task distribution. Ship the pair with a single-agent control arm on the same golden tasks and adopt on the measured Pareto frontier.

## Open questions

- Checkbox/progress ownership is genuinely unsettled — two shipped orchestrators do the exact opposite thing and no source argues for either. Pick one, state it in both files, and treat it as a decision to revisit rather than a best practice.
- The six-outcome return taxonomy is an ORIGINAL COMPOSITION, not an observed convention. After targeted search, no public source publishes a failure/replan outcome taxonomy for a prompt-string agent boundary, a planner-side dispatch table mapping outcomes to actions, or a writeup on recovering from an implementer that edited three of seven files. The closest published vocabularies are all coarser: Claude Code agent teams has exactly three task states (pending/in progress/completed) with NO failure state; Cline/Osmani add `blocked` meaning dependency-blocked rather than decision-blocked. Justify each outcome by its distinct dispatch consequence, not by precedent.
- No public prompt or doc covers a planner SUBAGENT that writes a plan file which the parent then auto-discovers without the subagent stating the path. Every real implementation either has the planner return the plan as text (Anthropic's built-in Plan agent, spec-spine's architect) or has a human/command resolve the path outside the agent layer. If this pair needs that combination, it is new design — mandate an explicit last-line `PLAN_FILE: <absolute path>` contract and TEST it rather than assuming discovery works.
- There is no published, validated grader for 'does this plan name real file paths and real symbols'. The obvious implementation (regex path-like and identifier-like tokens, assert they resolve in the checkout, score the fraction) is trivially buildable and its false-negative direction is safe — but it is unvalidated, and it plausibly catches only EP-1-shaped failures (~33%), not the semantic majority (edge cases, condition judgments, relational phrases ≈ 51%).
- Whether the HKUST 'Plan Reward' embedding-drift metric correlates with human plan-quality judgments is NOT established in the paper. Use it as a regression tripwire against a baseline, never as an absolute quality score.
- The `plansDirectory` settings key is documented by community references and appears in real `.claude/settings.json` files but was not found in Anthropic's own settings reference page. Verify before building a handoff on it.
- Kiro's docs document the three-file spec layout but NOT how an agent discovers which spec is active — selection appears to be an IDE UI action. Do not cite Kiro as the exemplar for path-free discovery; the working exemplars are Spec Kit's resolver script (`check-prerequisites.sh --json` printing FEATURE_DIR) and handoff-kit's registry-plus-recency-glob with a mandatory announcement of which one it picked.
- The 40-60% context-utilization ceiling is practitioner-reported (ACE-FCA), not a measured optimum. Treat it as a defensible default that happens to agree in direction with the context-rot benchmark, not a validated threshold.
- The specific SWE-bench degradation figures for multi-agent architectures (-2% to -15%, Terminal-Bench Centralized -19.2%, saturation at ~45%) came from secondary summaries and could not be verified in the primary PDF. The direction is supported; the numbers are not.
- The claim that LLM-generated AGENTS.md/CLAUDE.md files are net negative (≈ -3% versus ≈ +4% for human-written) is blog-grade and untraced to a primary study. Directionally consistent with the general finding that self-generated context adds distractors, but do not cite it as measured.
- Whether five- or six-way outcome granularity is right at all is untested. If two outcomes produce the same planner action in practice, merge them — the taxonomy earns its complexity only through distinct dispatch consequences.
- Anthropic's own coordinator prompt says 'Do not set the model parameter' for generic workers, which directly contradicts the plan-driven model-routing pattern from handoff-kit. Unresolved whether per-task model routing beats a uniform default in practice; measure it as a variable in the A/B rather than assuming.
